Abstract

A frozen vision-language model (VLM) can draw a navigation trace over a first-person image for a task and an embodiment without task-specific training. However, a zero-shot method fails in one of two ways. Some models chain points without settling a destination, so the trace wanders from the task, which we call the wandering trace. Others reach an accurate trace only after long reasoning that a robot pays for in latency and price, which we call the reasoning cost. We present PRISM-Nav, a Procedural Reasoning Interface with Structured output for Model-agnostic zero-shot navigation trace generation, a decision harness that specifies what a frozen VLM decides and in what order within one call. A decision schema bounds the waypoints and asks for the goal before the path, a single-call procedure orders the remaining decisions, and a deterministic repair corrects the output. Ablations show that the schema recovers the accuracy and the order of the stages removes the reasoning. On API and open-weight backbones from four vendors, PRISM-Nav raises accuracy by up to 79 points on the benchmark score and 51 points at equal resolution and lowers latency by up to 58 percent on Gemini 3 Flash. A wheeled robot and a humanoid robot execute its traces.

Two ways a zero-shot trace fails

The wandering trace

Some backbones follow the requested format but chain points without a settled destination. The trace wanders and ends away from the task.

The reasoning cost

Other backbones reach an accurate trace only after long reasoning, which a robot pays for in latency and in price at every decision.

Which failure appears depends on the model. PRISM-Nav addresses both without being tuned to either. Rather than changing how the model reasons, it specifies what a frozen VLM decides and in what order, inside one call and with one configuration for every backbone.

Method

Overview. (a) The call receives a first-person image, a task, and the name of an embodiment. (b) The single-call procedure asks for one decision per stage, and the overlays illustrate the decisions that accumulate inside the call. (c) The call returns one object that follows the decision schema, the deterministic repair corrects its start point and coordinate range, and the local navigation stack executes the trace.

removes the wandering trace

Decision schema

The output is a typed object written in a fixed order, the embodiment, a semantic goal, a grounded goal, an executed goal, and the trajectory. A bound of four to six waypoints ends the chaining, and a goal written before the path sets where the path ends.

removes the reasoning cost

Single-call procedure

Six ordered stages, each asking for one decision inside the same call. They are the scene check, goal candidates, goal selection and commitment, safety, social norms, and the trace. No stage may revise an earlier one, so the model does not have to find its decisions on its own.

corrects the form

Deterministic repair

Every waypoint is clamped to the image, and the start point is prepended when the first waypoint lies farther than 0.03 from it. The same output always yields the same trace, before scoring and before execution.

Results

We evaluate on the NaviTrace benchmark (evaluation code), where a trace is scored against the reference traces of its image by dynamic time warping, final displacement error, and a semantic penalty on the terrain it crosses. The baseline is the zero-shot prompt of the benchmark, and PRISM-Nav replaces only that system prompt.

Two controls on the order of the decisions. A generic plan-and-solve instruction raises the reasoning, whereas the ordered stages keep it low even when the goal is written after the path.

  • The waypoint bound ends the chaining. It leaves the reasoning tokens of both Gemini backbones unchanged.
  • The goal written before the path sets the endpoint. It helps where the backbone places the goal closer to the reference than it ends a free path. Given the reference endpoint, PRISM-Nav reaches 57.7, 70.4, and 72.7, so the remaining error lies mostly in the goal.
  • The order of the stages removes the reasoning. Without their order the same stages raise the reasoning tokens, and in order they lower them to 32 and 195 with the score unchanged at equal resolution.

Implementation notes

  • The executed goal is a check on the output. Without the executed goal field, GPT-5.4 nano scores 17.05 against 17.42 for PRISM-Nav on the validation split (paired Wilcoxon p = 0.77), so the field does not change the score.
  • Serving of Gemini 3 Flash. Gemini 3 Flash reasons at low effort only when Google Vertex serves the call, so its reasoning-on rows are served by Vertex and its reasoning-off rows by Google AI Studio.

Real-world deployment

A local navigation stack lifts each waypoint into three dimensions by projecting the local map of a LiDAR-inertial odometry into the image, and a local planner follows the lifted waypoints. Every trial issues a new decision of the model. T1 asks the robot to go upstairs, which for a wheeled robot means reaching the entrance of the elevator, and T2 asks it to go to a building across a road.

Prompts

PRISM-Nav replaces only the system prompt of the benchmark. Each (image, embodiment) pair is one call with the system prompt, the image, and the user message of the benchmark, at temperature 1.0, low reasoning effort, and an output limit of 5,000 tokens. The deterministic repair is applied to the returned trajectory.

PRISM-Nav system prompt 
You are a navigation expert.

Given a **first-person image**, a **navigation task**, and an **embodiment**, you must produce a **goal point** and a **trajectory**.

## CRITICAL INSTRUCTION

Work through the following stages IN ORDER. Each stage makes exactly ONE decision. Complete each stage internally before moving to the next; do not output anything until the final Output stage. Later stages MUST NOT revise earlier decisions.

## General Assumptions

- The image is a first-person view. The agent starts near the bottom center, at approximately [0.5, 0.95].
- Coordinates are normalized: (0,0) = top-left, (1,1) = bottom-right.

## Embodiment Movement Characteristics

- **Human**: A standard pedestrian. Can navigate stairs and ramps but cannot climb tall obstacles.
- **Legged Robot**: A quadruped like ANYmal. Behaves similarly to a human, but it is shorter. It can handle stairs and escalators.
- **Wheeled Robot**: A wheeled delivery robot. Behaves like a wheelchair, preferring smooth surfaces such as walkways and ramps. It cannot use stairs or escalators.
- **Bicycle**: A standard cyclist. Follows traffic regulations and prefers bike lanes or streets. Cannot navigate stairs.

# STAGE 1 - SCENE CHECK (internal)

Look at the image and task.
- needs_social: true if pedestrians, crosswalks, sidewalks, or bike lanes are visible
- scene_complexity: simple | standard | complex
- keep one sentence of evidence in mind

# STAGE 2 - GOAL CANDIDATES (internal)

Propose 3 navigation goal points for the task. Viewpoint near [0.5, 0.95].

- G1 (conservative): safe, closer
- G2 (standard): balanced
- G3 (exploratory): further, more ambitious

For each candidate, determine a semantic_goal_point (approximate high-level intent) and a grounded_goal_point (visually precise pixel location in the image).

# STAGE 3 - GOAL SELECTION (internal, then FROZEN)

Select the most task-relevant goal among G1, G2, G3.
From here on, the selected grounded_goal_point is FROZEN: no later stage may move it.

# STAGE 4 - SAFETY (internal)

Identify physical hazards from the image. For each, note its location (x, y) and its effect (allowed / avoid / no_go) for the current embodiment. Focus on obstacles, barriers, traffic, drop-offs, stairs.

# STAGE 5 - SOCIAL (internal; only if needs_social)

Identify social navigation cues from the image. For each, note its location (x, y) and its type: preferred_transition, preferred_corridor, or avoid_area. Focus on crosswalks, sidewalks, lanes.

# STAGE 6 - TRAJECTORY

Generate a trajectory from [0.5, 0.95] to the goal for the given embodiment. Avoid no_go hazards. Follow social hints. Stay on traversable terrain. Use 4-6 normalized (x, y) waypoints. executed_goal_point must equal grounded_goal_point.

## Output Format (JSON only)

```json
{
  "Embodiment": "",
  "semantic_goal_point": [x, y],
  "grounded_goal_point": [x, y],
  "executed_goal_point": [x, y],
  "trajectory": [[x1, y1], [x2, y2], ...]
}
```

All coordinates are normalized image coordinates in [0, 1]. Do not output stage notes or any other text.
User message of the benchmark (unchanged) 
**Embodiment**: {embodiment}
**Task**: {task}

The image shows a first-person view from the embodiment's current position. Begin your trajectory near the bottom center of the image (around normalized coordinate [0.5, 0.95]) and predict the path forward as a list of 2D points in normalized coordinates (values from 0 to 1) according to the embodiment and the scenario shown in the image.
